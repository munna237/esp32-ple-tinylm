Latency and memory characterisation

Where the bytes live

A language model on a microcontroller keeps almost all of its parameters in flash and reads them back every token. We measured what that costs. The answer is a dominance relation rather than a trade-off: capacity placed in flash is nearly free, capacity placed in the compute core is not.

What the measurements show

Four results, each with a control

01 · DOMINANCE

Flash-resident capacity is nearly free

At a fixed core budget, growing the per-layer table eightfold costs under 0.7 % of throughput. A configuration with 25 % fewer core parameters and four times the table is both faster and better than its core-heavy counterpart at every clock tested. Six of eleven transformer configurations sit on the frontier; every dominated one spent parameters on the core or on width instead.

02 · COST MODEL

Four fifths of a token is compute-bound

Per-token latency splits into a component that scales with the clock and a remainder that does not. Fitting on two clocks and validating on a third gives 0.48 % mean error across both families. The model holds from 80 to 240 MHz and breaks below that, where the flash interface stops tracking the CPU.

03 · ATTRIBUTION

Halving flash bandwidth costs under 5 %

Every weight is read from flash on every token, yet narrowing the bus from quad to dual I/O changes total latency by 4.4–5.0 %. The output head is the only stage resident in PSRAM and the only one that does not respond — a null control confirming the per-stage timers attribute cost to the right memory tier.

04 · INTERVENTION

The KV cache is what makes latency grow

Transformer latency rises with position; recurrent latency does not. Rather than infer the cause we built the counterfactual — LSTM and GRU models on the same task, tokenizer, embedding and output head, differing only in carrying no cache. Their latency is constant to three significant figures across a fourfold change in generation length.

How a number gets made

One run, start to finish

Each cell is five runs, and the whole sweep was executed twice in separate sessions with the board powered down between them.

Verify

The C runtime is checked against dequantised PyTorch logits. Max absolute difference 1e‑5. No board time until it passes.

Build

Clock, flash mode and optimisation level are set in the build, not at runtime.

Flash

Model payload written to 0x110000, then a hardware reset over RTS.

Capture

200 tokens, greedy, fixed prompt. Five stage timers plus die temperature before and after.

Record

The firmware reports its own build tag and clocks into every row, so a setting that failed to take is visible in the data.

What this does not show

  • No live hardware. The panel above evaluates a fitted model in your browser. Nothing here is connected to a board.
  • One device. All measurements come from a single module. Device-to-device variation is not characterised.
  • No energy. Latency and memory only. For battery-powered deployment, joules per token is the binding constraint and remains unmeasured on this hardware class.
  • Quality is relative. Validation loss is comparable only within this 4096-token vocabulary family, which shares a tokenizer and training budget. These models generate fluent text in one narrow domain and cannot follow instructions or answer questions.
